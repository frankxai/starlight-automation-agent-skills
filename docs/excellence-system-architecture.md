# Starlight Excellence: quality architecture and integration ownership

Status: proposal implemented as versioned doctrine; not a deployed runtime.

## Canonical ownership
Source of truth: version-controlled Excellence protocol and skill in this repo, with PR review. Respect pre-existing repositories and instructions; publish via existing rule synchronizer once discovered and verified. Do not duplicate instruction controllers.

## Surfaces and contracts
- ChatGPT Personalization: short user-installed baseline; no plugin may silently enforce instructions in every chat.
- Starlight AI Architect: planning contracts, architectural critique and cited alternatives.
- Starlight Agent Designer: agent identity, role scopes, capabilities, mission templates and evals.
- Starlight Plugin Forge: packaging, deterministic builds and install receipts.
- Starlight Memory: feedback proposals, explicit consent, source trace, separation by tenant.
- GenCreator Native: content and media generation gates, originality and brand standards.
- Starlight Music Studio: song-specific emotional, lyrical, rhythmic and listening gates.
- Starlight Marketing Skills: claims, audience, narratives, conversions and testing.
- Starlight software factory: evidence-based CI, PR review and deployment receipts.
- Starlight Intelligence API: future metering and tenant-aware orchestration, NOT a deployed claim.

## Agent roles
Astra: architecture, thesis, opportunity discovery. Sol: production and implementation. Terra: bounded runtime and validation. Verity: independent adversarial reviewer. Atlas: research. Muse: editorial, narrative, visual and sonic art direction. Mercury: audience and distribution. Names are logical responsibilities; cannot be promised as running agents without endpoint and auth.

## Durable mission envelope
ID; tenant; objective; audience; brand; references and allowed provenance; input revision; deadline and resource budget; risk; authority and side effect limits; chosen model and role; owner; acceptance checks; output artifacts; reviewer identity; test record; release state; lessons.
Release state: proposed, implemented, tested, merged, deployed, operating, customer-validated. Never conflate states.

## Routing policy
Use proven benchmarks, latency, cost, available tools, data sensitivity and risk. Cost-efficient executors for mechanical bounded jobs only after successful evals; frontier reasoning for consequential architecture, ambiguity or difficult synthesis. Independent reviewer must be capable of checking relevant failure modes.

## Evals
Compare against fixed tasks; log model, prompt revision, source snapshot, output, cost, elapsed time, objective check results, independent judgment, and failures. Avoid Goodhart's law: rubric scores never override critical failures.

## Boundaries
No unapproved credential use, hidden cross-account writes, background workers without an actual scheduler, fabricated tool access, or unsupported claims of quality. Customer/project isolation first.
